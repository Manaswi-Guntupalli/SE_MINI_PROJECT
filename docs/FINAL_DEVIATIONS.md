## Changes to requirements and validation scope

| Earlier baseline | Reviewed implementation and reason | Traceability |
|---|---|---|
| Original FR-15 and October agreement specified **+1** for a correct answer and maximum equal to question count. | A correct answer earns the question's published marks. Wrong and unanswered responses earn zero. Maximum is the sum of published marks. Marks can be fractional and must be at least 1 within the supported safe range. A legacy question without marks defaults to 1. This makes the Instructor's Marks setting effective and preserves existing one-mark exams. | QUES-FR-01/02, EVAL-FR-01, TC-QUES-01/02, TC-EVAL-01. [Scoring rules](../server/services/scoring.js) and [weighted results tests](../server/test/results-workflow.test.mjs). |
| Draft authoring descriptions treated incomplete MCQs as invalid at save time. | Instructors can save incomplete options in a Draft. Publish requires nonblank question text, at least two nonblank options and exactly one correct option per question, plus valid exam fields. Published definitions are immutable. This lets Instructors save work in progress and keeps Student exams valid. | QUES-FR-03, EXAM-FR-04, TC-QUES-03, TC-EXAM-04. [Exam controller](../server/controllers/examController.js). |
| An early listing interpretation showed only currently startable exams. | Students see Published scheduled exams with their eligibility and own attempt state. Drafts stay hidden and the server rejects early Start. The original availability rule is enforced while future exams are visible. | ATT-FR-01/02, TC-ATT-01/02. [Student API](../server/routes/studentRoutes.js). |
| Original portability text named Chrome, Edge and Firefox. | The Version 1.3 acceptance target is the core workflow on Chrome and Edge. The retained local named-channel report covers those two browsers. Firefox has no validation record in the reviewed evidence. | OEP-NF-003, TC-NF-COMP-01. [Browser report](evidence/checkpoint-2026-11-04/SYSTEM_VALIDATION_REPORT.md). |
| Early planning referenced Docker, SonarQube or equivalent validation, and a local CI server was considered. | GitHub Actions is the sole CI provider. Locked installs, ESLint, backend syntax checks, automated tests and V8 coverage are the recorded checks. Docker and SonarQube have no delivered verification evidence. Any earlier tooling obligation requires an evaluator decision. | [CI tooling decision](CI_TOOLING_DECISION.md) and [current test report](FINAL_CHECKPOINT_REPORT.md). |

## Design changes and implementation refinements

| Earlier design or assumption | Reviewed design and reason | Traceability |
|---|---|---|
| Preliminary `/api/attempts` and `/api/results` routes and alternative field names appeared in planning. | Student routes are grouped under `/api/student`. Instructor results use `GET /api/exams/:id/results`. Canonical fields include `User.email`, `User.active`, `Attempt.deadline` and `Result.maximum`. Options embed `text` and `isCorrect` in owned exam questions. Responses and Results use separate collections with unique indexes. The separation supports ownership and one durable result per attempt. | SAD interface and data design. [Student routes](../server/routes/studentRoutes.js), [Response model](../server/models/Response.js) and [Result model](../server/models/Result.js). |
| The original SRS required versioned or serialized writes and a server expiry process. | Both current PUT and legacy POST answer saves require `expectedRevision`. Stale writes return 409. The client distinguishes desired from acknowledged answers. MongoDB time gates writes and the expiry worker polls every five seconds by default. Manual and timeout paths share transactional finalization. Submitted/Pending stays closed while evaluation retries. These choices implement the original durability and deadline requirements. | ATT-FR-03/04/05/06, EVAL-FR-02, TC-ATT-03, TC-TIME-01, TC-SUB-01/02, TC-EVAL-02. [Persistence service](../server/services/persistenceService.js) and [worker](../server/services/evaluationWorker.js). |
| Earlier release behavior used one point per question for previously evaluated results. | A dedicated maintenance command previews corrections by default and requires explicit `--apply` to update. It recalculates from the published exam and saved answers, corrects only rows matching the legacy scoring algorithm and skips inconsistent associations or totals. The test covers repeat-safe application. Ordinary evaluation keeps one immutable result. | EVAL-FR-02, TC-EVAL-02. [Repair service](../server/services/repairWeightedResults.js) and [maintenance entry point](../server/scripts/repairWeightedResults.js). |
| Earlier role and UI flows did not handle several delayed or concurrent requests. | BUG-01 guards Instructor requests across account switches. BUG-02 serializes access changes and preserves an active Admin. BUG-03 separates attempt recovery from list loading. BUG-04 ignores stale list responses. BUG-05 preserves an unavailable list after error dismissal until a successful retry. These fixes protect account isolation, attempt recovery and accurate UI state. | TC-AUTH-03, TC-ADMIN-01, TC-ATT-02, TC-NF-ERR-01. [Defect and regression record](../README_FINAL_BUG_CHECK.md). |
| Early tooling proposed Jest as the primary test runner. UI planning included Bootstrap or an earlier dark interface. | The primary suites use Vitest with Supertest and React Testing Library, standalone Node scoring tests and Playwright system tests. The current lavender UI uses shared React components and custom CSS, integrated through PR #71. The seven optional Jest security executions belong to the November 4 baseline. | Test Plan sections 5 and 13. [Test workflow](../.github/workflows/application-ci.yml) and [UI design](UI_DESIGN_SYSTEM.md). |

## Baseline references and final demo

The original PDF SRS and October scope agreement preserve the historical fixed-scoring rule. Some older repository references also repeat it, including the November 5 [API contract](AUTH_AND_EXAM_API.md) and [submission checklist](FINAL_SUBMISSION_CHECKLIST.md). For the final demo, use the Version 1.3 SRS and SAD and the current scoring code. The older checklist’s counts and coverage describe its earlier evidence snapshot. Use the [final checkpoint test report](FINAL_CHECKPOINT_REPORT.md) for current figures.

The original proposal described an earlier sprint sequence. The repository project plan records Sprint 1 as October 19–23 and Sprint 2 as October 26–30, with later integration and validation recorded on their actual dates. The final review and release freeze require the team's recorded acceptance. [Project plan](05_Project_Plan.md)

For the scoring demo, publish questions worth **5, 2.5 and 3 marks**. The maximum is **10.5**. An attempt that answers only the second question correctly earns **2.5/10.5**. For the reliability demo, restore an active attempt after a list error and let a second attempt expire after closing the browser. These scenarios have recorded test evidence. The tooling substitution, formal approval and production deployment are separate acceptance matters.
