# Final design and implementation changes

Prepared 5 November 2026 for review. The final application is the release integrated through PR #71 and promoted by PR #70 to main (`13ec998`). This document records existing implementation decisions; it introduces no extra features. The original proposal, PDF SRS, XLSX and earlier dated evidence remain historical sources. Current authoritative specifications are the three [Part 1 documents](part-1/README.md).

| Initial or earlier description | Implemented contract and reason | Traceability |
|---|---|---|
| Incomplete MCQs cannot be saved | Drafts may contain incomplete options while being authored; publication requires nonblank text, at least two nonblank options and exactly one correct answer. Prevents invalid published exams without blocking draft work. | QUES-FR-03; #35/#36; AC35 and IT-PUBLISH |
| Only currently eligible exams appear | Published future exams are visible as scheduled; the server disables/rejects early Start. Drafts stay hidden. Own Start/Resume/Expired/Submitted states are explicit. | ATT-FR-01; #38/#39; AC36-01 and AC38-LIST |
| Preliminary /api/attempts and /api/results paths | Student endpoints are under /api/student; Instructor results are under /api/exams/:id/results. Question writes use embedded options with isCorrect. The SAD API table and [contract](AUTH_AND_EXAM_API.md) now describe actual routes and response shapes. | ATT/RES and SAD section 4 |
| Alternative user and result names, embedded response proposals | Canonical fields are User.email/active, Attempt.deadline and Result.maximum. Questions/options are embedded; Response/Result use separate collections with unique indexes and transaction-safe associations. | #20/#22/#52; [Field Layout](OEP-18_Field_Layout.md) |
| Simple answer overwrites | Both current PUT and legacy POST saves require expectedRevision. The UI serializes rapid saves, separates desired from acknowledged answers, and handles 409 reload/retry. This prevents delayed old choices replacing acknowledged new ones. | #40; AC40-ORDER/REVISION/LEGACY |
| Browser timer and submission alone | Server deadline and MongoDB time control writes/finalization. A monotonic synchronized UI locks at expiry; a 5-second default worker finalizes browser-closed expiry and retries evaluation. Submitted state stays durable and results are idempotent. | #46/#47/#48; OEP44-ST-02 and transaction/race tests |
| Jest as the principal runner | Vitest integrates with the Vite client, Supertest and Testing Library. Node test covers scoring; Playwright covers real browsers. Seven retained Jest security cases were also executed separately. | Test Plan section 5; [unit report](evidence/checkpoint-2026-11-04/UNIT_REPORT.md) |
| Bootstrap or an older dark interface | Shared custom CSS and React components provide the lavender UI from Manaswi's branch. Its source was reconciled through #71 with the latest service and security fixes, preserving original contribution history. | #66/#67/#71; [UI design](UI_DESIGN_SYSTEM.md) |
| External/local CI server, Docker and SonarQube named in planning | GitHub Actions is the actual sole CI provider. ESLint/syntax, real tests and V8 line/branch reports are evidenced. Docker, SonarQube, deployment and production HTTPS are not claimed as delivered. The supplied checkpoint PDFs focus on SDLC and permit explained changes; evaluator acceptance of any earlier course-tool substitution must still be confirmed. | [CI decision](CI_TOOLING_DECISION.md); [CI guide](CI.md) |
| Original planned sprint dates and freeze | Planned sprints remain 19–23 and 26–30 October. Later integration/validation dates are recorded honestly. On 5 November the requester asked to finish the checklist for review; feature scope is frozen for this candidate. Owner acceptance/merge remains pending review. | [final checklist](FINAL_SUBMISSION_CHECKLIST.md) |

The local 30-active-user benchmark excludes login/bootstrap and external networking; it is not login-burst or production capacity certification. Chrome/Edge versions, coverage scope and raw observations are retained. No claim is made that every one of the initial workbook's 188 proposed scenarios was independently executed.
